Get started
API Endpoint: {BASE_URL}/api/public/{API_KEY}
To use this API, you need an API key.
Generate your own API key from
Account Settings (Pengaturan Akun) in the Mengantar
app. This works the same way in sandbox and in production; each
environment issues its own key.
Base URL :
⚠ Ninja is discontinued — effective 1 September 2026
Starting 1 September 2026, Ninja is
no longer available on the Mengantar public API:
Check Shipping Fee (cek ongkir) —
Ninja is no longer a valid
courier value and is no longer returned as a
selectable rate.
Create Order — new shipments can no
longer be created with Ninja.
Pay Unpaid — unpaid
Ninja orders can no longer be paid, because
completing the payment generates the tracking number and creates
the shipment. Contact Mengantar support for any left over from
before the cut-off.
Existing Ninja data is not affected —
orders and batches created before the cut-off can still be
retrieved and tracked through the read endpoints (Get orders, Get batches) as usual.
Direct Check Shipping Fee requests with
courier=Ninja return HTTP 400 with
code: COURIER_DISABLED. Historical order and batch
reads remain available for both couriers.
Print Label PDF (BETA) — asynchronous
This API creates a PDF label in the background. There are two
separate endpoints: Request creates a generation job; Get returns
its current result.
Request never returns a download URL. A URL is
returned only by Get when the status is COMPLETED.
1. Request Label Generation
POST
{BASE_URL}/api/public/{API_KEY}/label-generation
Submit one paid order with an available tracking number. The order
must belong to the account that owns the API key. This endpoint
accepts exactly one orderId; arrays and comma-,
semicolon-, or space-separated order IDs are rejected. The API key
must have the labelGeneration permission.

Required
Description

One existing, non-deleted order ID owned by the API key
account.
courier

Yes
The courier of that order, for example JNE,
JT, or spx (SPX Express).

String
Yes

Store labelGenerationId and use it with Get. The
response deliberately has no downloadUrl, even if an
earlier request for the same active order and format is reused.
Several orders across couriers
Multi-order submission in one HTTP request is not supported. Send
one Request per order and retain one generation ID per request.
POST /label-generation
{ "orderId": "ORDER-JNE-001", "courier": "JNE", "format": "normal-1" }
POST /label-generation
{ "orderId": "ORDER-JT-002", "courier": "JT", "format": "thermal-new-10x15" }
POST /label-generation
{ "orderId": "ORDER-POS-003", "courier": "POS", "format": "normal-2" }
Each response: HTTP 202
{ "success": true, "data": { "labelGenerationId": "<unique-id>", "status": "PENDING" } }
2. Get Label Generation Status
GET
{BASE_URL}/api/public/{API_KEY}/label-generation/{labelGenerationId}
labelGenerationId is the 24-character ID returned by
Request. Get is read-only and does not consume the Print action
limit. Poll at a reasonable interval; do not submit a new Request
merely to check progress. The API key must have the
labelGeneration
permission.

Rate limit
Request Label Generation is a final Print action. The limit is
8 Print actions per 60 seconds, shared between
Seller Web and Public API for the same parent account. A valid
Request uses one action even when it returns an existing active
generation. Get Status does not use this limit.

⚠ Notes
Ninja (discontinued 1 September 2026) —
direct requests with courier=Ninja return HTTP 400,
success: false,
message: "Courier is not available", and
code: "COURIER_DISABLED". With
courier=all, Ninja,
NinjaCargo are omitted. Historical order and batch
read endpoints continue to accept these couriers.
Possibilities for unsupported and unsupported_cod:
if unsupported true and unsupported_cod
true — CAN'T send to destination BOTH COD AND
NON COD
if unsupported true and unsupported_cod
false — CAN'T send to destination BOTH COD AND
NON COD
if unsupported false and unsupported_cod
true — can't send COD BUT still CAN send Non
COD
if unsupported false and unsupported_cod
false — can send COD or Non COD
Discount calculation is based on user's shipping volume, refer
to
Diskon Ongkos Kirim. Unlike /allEstimatePublic which has a fixed 20%
discount.
Pos Indonesia COD eligibility: COD requires a
delivered rate of at least 82%. The rate is
calculated across orders from all couriers created in the
rolling 21–60 day window. If the rate remains
below the threshold, a
three-day grace period applies before Pos
Indonesia COD is blocked. Non-COD service is not affected by
this eligibility rule. For a DG request,
isDangerousGoodsSupported indicates courier
capability while unsupported indicates destination
coverage. Check both fields before creating an order.
SPX Express (spx) limits: maximum weight
50 kg, maximum COD amount
Rp5,000,000, maximum Non-COD goods value
Rp10,000,000.

IDEMPOTENCY KEY (OPTIONAL)
A create order request can time out on your side while Mengantar is
still creating the batch. Retrying it then creates the same orders a
second time. To retry safely, send the
idempotencyKey header with a reference from your own
system for this request, for example your order or batch number, and
send the same value again on every retry of that request.
curl --location '{BASE_URL}/api/public/{API_KEY}/order' \
--header 'Content-Type: application/json' \
--header 'idempotencyKey: INV-2026-0001' \
--data '{ ...same body as above... }'
Header
Type
Description
idempotencyKey
String
(Optional). 1–50 characters; leading and trailing spaces
are ignored. A key is remembered for 24 hours
from the first request that used it, per API Key account: the
same key from another account is unrelated. Without this
header the request is processed exactly as before. It is read
from the header only, never from the body, and is ignored on a
validate request.
Two requests are the same request when they carry the same key and
the same body (the order of JSON fields does not matter).
HTTP status
Condition
Same as the first request
The key was already used with the same body and that request
has finished. The first response is returned again, with the
same batch, batch_id and per-order
results, and no new batch or order is created. The response
carries the header Idempotent-Replayed: true and
the field "idempotentReplayed": true. The orders
are as they were when first created; use
GET /order for their current status. This applies
to a first request that failed with a 5xx too: it may have
created part of the batch, so it is not run again.
400
code: IDEMPOTENCY_KEY_INVALID. The header is empty
or longer than 50 characters. No batch is created.
409
code: IDEMPOTENCY_REQUEST_IN_PROGRESS. The first
request with this key is still being processed. No batch is
created. Retry with the same key after the number of seconds
in the Retry-After header to get its result.
409
code: IDEMPOTENCY_REQUEST_UNRESOLVED. The first
request with this key never finished. It may have created some
orders, so it is not run again: check GET /order
and send any missing orders with a new key.
422
code: IDEMPOTENCY_KEY_REUSED. The key was already
used for a request with a different body. No batch is created.
503
code: IDEMPOTENCY_UNAVAILABLE. The key could not
be checked. No batch is created; retry with the same key.
When the first request is rejected with a 4xx before any order is
created (for example a validation error), the key is released: fix
the body and send it again with the same key.
A replay is a copy of the first response, not the current state of
its orders. Deleting the batch or its orders (see
Delete Batch) does not release
the key: sending the same key again still returns the old response,
with "idempotentReplayed": true and the old
batch_id and AWB numbers, and no new order is created.
To create the orders again after a delete, send them with a
new key. Use GET /order to check
whether the orders are still active.
Recommended retry flow
Send the request with idempotencyKey set to your own
reference, for example INV-2026-0001.
If the connection times out or drops, send the
exact same body again with the
same key. Do not regenerate values that change on
every call (timestamps, random IDs), or the retry is seen as a
different request.
On 409 IDEMPOTENCY_REQUEST_IN_PROGRESS, wait for the
Retry-After seconds and retry with the same key.
Stop when you get the batch back (a first response, or a replay
with "idempotentReplayed": true).
On a replayed 5xx or
409 IDEMPOTENCY_REQUEST_UNRESOLVED, check
GET /order first, then send only the missing orders
with a new key.

PAGINATION
A page holds at most 100 records
(size, default 50) and page goes up to
100. Beyond that, or for any list longer than a few
pages, read with cursor: send the
nextCursor value of the previous response and repeat
until it comes back empty. A cursor page is exact at any depth and
costs the same whether it is the 2nd or the 500th.
# First page
curl -X GET '{BASE_URL}/api/public/{API_KEY}/order?size=100'
# Next page: pass nextCursor from the previous response
curl -X GET '{BASE_URL}/api/public/{API_KEY}/order?size=100&cursor=MjAyMi0wOS0xNVQw...'
The response carries nextCursor: an opaque string for
the next page, or an empty string when the page returned is the last
one.
Without dateRange the list covers orders that have not
been archived yet (roughly the last 6 months), across the couriers
your account has orders in. To read older orders, send a
dateRange that covers them. Looking up a single order
by order_id or tracking_id always searches
the archive as well.
Without courier the page is merged across every courier
your account uses, so page × size may not
exceed 1,500 there (page 15 at size 100, page 30 at
size 50). To go further back, name a courier or use
cursor. The same ceiling applies to a single courier
when the dateRange starts more than six months back (or
a lookup sends no dateRange), because such a page is
merged from current and archived orders.
Requests above the limits are rejected before any data is read:
{ "success": false, "message": "size must not exceed 100; use cursor to fetch the next page" }
{ "success": false, "message": "page must not exceed 100; use cursor (or dateRange) to go further back" }
{ "success": false, "message": "page x size must not exceed 1500 without courier; send courier or use cursor to go further back" }
{ "success": false, "message": "page x size must not exceed 1500 when the date range reaches the archive; use cursor to go further back" }
{ "success": false, "message": "Invalid cursor; send the nextCursor value from the previous response" }

Delete Orders
An order can only be deleted while its status is still
active, error,
PENDING PICKUP, PICKUP FAILED, or
PICKUP_FAILED_API (or has no status yet). This rule is
the same for every courier — once an order moves past pickup (picked
up, in transit, delivered, RTS, etc.) it can no longer be deleted
through this endpoint, and the request simply skips that order.
⚠ Notes
Anteraja — orders can only be deleted
after 5 minutes from order created. Deleting
before that returns an error asking you to wait.
All other couriers (JNE, SiCepat, Sap,
iDexpress, JT, Ninja, Lion, Paxel, POS, SPX) — there is no
fixed waiting time on Mengantar's side once the order already
has a tracking number. The delete request is forwarded to the

Webhook
Instead of polling
GET {BASE_URL}/api/public/{API_KEY}/order, you can have Mengantar push order status updates to your own URL.
Sandbox: webhooks are open to every sandbox account, with
no whitelist and nothing to request. Sandbox orders never move on
their own, so you trigger the delivery yourself: every successful
Simulate order status call
sends one webhook carrying the new
status_category, even when it is
the same as before. Every delivery from the sandbox carries the
header x-environment: sandbox;
production deliveries carry no such header. Still use a different
Webhook URL in sandbox than in production, so a rehearsal can
never be mistaken for a real shipment update. Everything below
behaves the same in both environments.
Set your Webhook URL in
Settings → Account → Integrasi Public API. Saving
it requires a verification code, and generates your
Webhook Secret the first time. The URL must use HTTPS, must
not point to an internal address, and is limited to 512 characters.
In sandbox every account can set one, with nothing
to request. In production webhooks are enabled per
account while the rollout is staged, so the Webhook section only
appears once your account has been enabled — ask the Mengantar
team if you do not see it yet.
What we send
We send a POST with a JSON body
every time the order status changes.
POST https://your-domain.com/webhook
Content-Type: application/json
x-timestamp: 1787548800000
x-signature: 05826dec707ea7164801d952cb7eaf7ce9adc0c8aa0b93366480434164a1a111
{
"cnote_no": "JNE1234567890",
"order_id": "ORD-000123",
"courier": "JNE",
"status_category": "DELIVERED"
}

Description

Tracking number (AWB) of the order.
order_id
Mengantar order number.
courier
Courier handling the order.
status_category
The only status we send, and the one to build your logic on.
The raw courier status is deliberately not included: its
wording is open-ended and differs per courier, so branching on
it would mean writing per-courier handling.
This is the same status category your orders already carry, so
the values differ per courier. For the complete per-courier

matching an exhaustive list. One case deserves particular
care: a cancellation arrives as
CANCELED from some couriers
and CANCELLED from others
— handle both spellings.
Telling sandbox from production
A delivery sent from the sandbox environment carries one extra
header, x-environment: sandbox. A
production delivery carries no
x-environment header at all. The
body is identical in both environments and the header is not part of
the signature, so a receiver that ignores it keeps working; one that
reads it can refuse to act on a sandbox update even if it ever
reaches a production URL. We still recommend a separate Webhook URL
per environment rather than relying on the header alone.
POST https://your-domain.com/webhook
Content-Type: application/json
x-environment: sandbox
x-timestamp: 1787548800000
x-signature: 05826dec707ea7164801d952cb7eaf7ce9adc0c8aa0b93366480434164a1a111
Verifying the request
Every request carries
x-signature and
x-timestamp. Checking them is
optional — your endpoint receives updates either way
— but we strongly recommend it, and it takes about ten lines.
Why it matters
Your Webhook URL sits on the public internet, and anyone who learns
it can send it a request. A leaked log, a screenshot in a support
ticket, a former employee, or simply a guessable path is enough.
If you act on whatever arrives, someone who knows your URL can post
a fake DELIVERED and mark an order
complete in your system before it ever shipped. We do not send from
a fixed set of IP addresses, so an IP allowlist is not an option:
the shared secret is the only thing that separates a genuine update
from a forged one.
The two headers give you two different guarantees:
Header
What it proves
x-signature
The request came from Mengantar and the body was not modified
along the way. Only someone holding your Webhook Secret can
produce it.
x-timestamp
When we sent it. Lets you reject an old, genuine request that
someone captured and is replaying now.
How to verify
The signature is an HMAC-SHA256, in hex, of
{x-timestamp}.{raw request body}, keyed with your Webhook Secret. Three steps:
Capture the raw request body, before any JSON parsing.
Compute the HMAC over
{x-timestamp}.{raw body}
using your Webhook Secret as the key.
Compare it to x-signature with a
constant-time comparison, and reject the request if they differ.
Compute it over the raw body exactly as received.
Re-serialising the parsed JSON can reorder or reformat it and will
not match.
Test vector
Check your implementation against this before going live. If your
code turns these inputs into the same signature, it will verify our
real requests correctly. The secret below is only for this example
— use your own Webhook Secret in production.

const crypto = require('crypto');
// express: keep the raw body so the signature can be checked
app.use(express.json({
verify: (req, res, buf) => { req.rawBody = buf.toString(); }
}));
app.post('/webhook', (req, res) => {
const expected = crypto
.createHmac('sha256', process.env.MENGANTAR_WEBHOOK_SECRET)
.update(`${req.get('x-timestamp')}.${req.rawBody}`)
.digest('hex');
const received = req.get('x-signature') || '';
const valid =
expected.length === received.length &&
crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received));
if (!valid) return res.sendStatus(401);
// optional: reject anything older than a few minutes
if (Date.now() - Number(req.get('x-timestamp')) > 5 * 60 * 1000) {
return res.sendStatus(401);
}
// ... update your order here ...
res.sendStatus(200);
});

If the signature never matches
Almost every failed integration is one of these:
Signing a re-serialised body. By far the most common cause.
Parsing the JSON and dumping it again changes key order and
spacing, so the bytes you sign are not the bytes we signed. Keep
the raw body.
The framework consumed the body first. In Express you need
the verify hook shown above,
because express.json() discards
the raw stream. Laravel keeps it — use
$request->getContent().
Forgetting the timestamp prefix. The signed string is
{x-timestamp}.{raw body}, not the body on its own. The separator is a single dot.
Using the wrong secret. Regenerating your API key also
replaces the Webhook Secret. If verification broke suddenly and
nothing else changed, check this first.
A plain == comparison. It
works, but it leaks timing information. Use
hash_equals,
hmac.compare_digest, or
crypto.timingSafeEqual.
If you choose not to verify at all, at least make your Webhook URL
path long and unguessable. That is a speed bump, not a substitute:
the path travels with every request we send and is not a secret.
Responding and retries
Answer with any 2xx status. We wait
at most 5 seconds, so acknowledge first and do your processing
afterwards. Redirects are not followed.
A failed delivery is retried up to 3 times, roughly 1s, 5s and 15s
later. Delivery is best effort: if all attempts fail the update is
not resent, so keep
GET {BASE_URL}/api/public/{API_KEY}/order
as your reconciliation path.
Deliveries are independent, so they can arrive out of order after a
retry. Use x-timestamp to decide
which update is newer rather than the order of arrival, and expect
the same status to arrive more than once.
If delivery is paused
If your endpoint fails to take 20 updates in a row within 24 hours,
we pause delivery to it automatically. A URL that has stopped
responding otherwise costs four outbound attempts on every status
change, indefinitely. Any successful delivery resets the count, so
occasional failures never accumulate toward it.
While delivery is paused,
Settings → Account → Integrasi Public API shows a
notice saying so and when it happened, and we send a notification to
the bell in your dashboard. If updates stop arriving, check there
first.
To resume, make sure your endpoint accepts requests again, then
press
Aktifkan kembali ("Reactivate") in that same section. Saving
your Webhook URL again has the same effect. Either way your Webhook
URL and Webhook Secret are kept as they are, and resuming does not
require a verification code.
Updates whose status changed while delivery was paused are
not resent. Use
GET {BASE_URL}/api/public/{API_KEY}/order
to reconcile anything you missed.
Pausing affects webhook delivery only. Your API key keeps working,
so creating orders and every other endpoint are unaffected.
Rotating the secret
You can regenerate the Webhook Secret on its own, without touching
your API key. Note that regenerating the API key also
replaces the Webhook Secret — your Webhook URL is kept, but
you will need to update the secret in your system.
